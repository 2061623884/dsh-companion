# 后台服务为什么还不能脱离桌面窗口启动

验证日期：2026-10-26。环境：Windows x64，已安装的 DeepSeek Harness Desktop 0.2.1-rc.2，DSH Companion 0.4.0-preview.1 源码。

## 目标与当前实现

目标是在 VS Code 直接新建或继续共享会话：插件使用桌面端安装的运行时、登录、配置和会话，后台未运行时自动启动；之后打开桌面端仍使用同一个后台。用户不必先手动打开桌面端。

当前实现能够连接已经运行的桌面 Host，并保留侧栏、工作区绑定和未保存代码引用。未安装时提示下载，已安装但未运行时提供“打开桌面端”。它尚未自动启动独立 Host。

## 实际复现结果

全部操作使用合成数据目录和隔离的 Electron 配置，不使用日常登录或会话，也不发送模型对话。

1. 使用已安装桌面程序自带的 Electron Node 模式和官方 `@deepseek-ai/dsh-desktop-host` 入口，启动后台 Host A。
2. 通过 Host A 的 `session/create` 接口创建合成会话。
3. 保持 Host A 运行，用同一个隔离 `DSH_HOME` 启动未修改的桌面程序，并为桌面程序指定独立 `--user-data-dir`。
4. 检查 Host 进程、父进程及本机监听端口，再分别调用 `session/list`。

| 检查项 | 结果 |
| --- | --- |
| 原 Host A 在打开桌面端后仍可访问 | 是 |
| 桌面端只连接已有 Host A | 否 |
| 桌面端启动了自己的 Host B | 是，父进程属于桌面程序，PID 和端口均不同 |
| Host B 可读取之前保存的合成会话 | 是 |
| 两个界面复用同一个后台实例 | 否 |

测试结束后已清理本次启动的隔离进程。原始进程信息、路径和诊断记录仅保留在忽略的本地测试目录中。

## 原因与实际影响

对已安装程序的只读检查表明，桌面外壳创建自己的 `DesktopHostProcess`，随后启动 Host 子进程。Electron 的单实例锁只处理桌面外壳的重复启动；独立的 Node 模式 Host 不持有这把锁。当前启动路径未发现连接已有独立 Host 的分支。

因此，“使用相同的运行时文件和数据目录”不等于“使用同一个运行中的服务”。读到已经保存的会话，只证明两边能够读取该记录，不能证明会话执行状态、流式消息、取消操作或后台任务由同一个实例管理。

本次没有验证两个 Host 同时写入时的数据完整性，也没有观察到或声称已经发生数据损坏。并发写入、实时同步、任务归属、退出及更新交接仍属未验证项，因此不能把这个双 Host 方案用于用户的日常数据。

## 后续必须解决的条件

需要让桌面端能够连接或接管已启动的共享后台，并明确后台发现、单实例归属、认证、退出及升级时的交接方式。如果安装版另有受支持的后台启动或接管接口，需要先找到并实际验证；当前证据不足以宣称已有这样的接口。

仅在插件里增加一个 `spawn` 调用不能满足目标。当前保留“连接已运行桌面端”的实现，不修改已安装的官方桌面程序，不自动启动另一个 Host，不迁移或删除日常数据。

## 验证范围与交付状态

连接单个现有 Host 的集成验证，以及两个受测 VS Code 版本中的安装验收此前已通过；这些结果不代表后台复用已经通过。托管 CI 尚需针对新架构配置桌面端准备步骤，历史运行时测试不能替代该验证。

本次交付为源码提交和问题记录，不创建标签、GitHub Release 或公开安装包。

## 2026-10-26 后续源码修复

进一步核查 Codex 和 DSH 开源代码后，采用配套桌面外壳的显式后台启动模式：由同一桌面实例继续拥有 Host，Companion 检查能力声明后请求后台启动，正常打开桌面端时展示已有窗口。此前对官方 Desktop 0.2.1-rc.2 的复现结论仍成立；此模式需要配套的新桌面构建，不能只给原版传入参数。

完整依据、两边的修改范围和剩余 Windows 验收见 [共享会话与后台启动源码修复方案](shared-session-solution.md)。源码补丁与原版安装的运行结果分别记录，不把回归测试通过当作原版已经支持后台复用。
