# Desktop connection preview

Companion is a client of the installed Windows DeepSeek Harness Desktop Host. Desktop owns its process lifetime, credentials, profile settings and sessions. The extension owns a loopback HTTP/WebSocket proxy, the editor bridge and its page-scoped UI adapter.

Desktop discovery identifies the installed executable and listeners belonging to the Desktop Host process. Startup distinguishes not installed, not running, authentication/not-ready and incompatible frontend states. The stock desktop requires the user's open action. A Windows build that ships the matching background-start capability may be started with the fixed `--background` argument on initial connection or an explicit reconnect action. Its Electron shell remains the only Host owner. Missing or unknown capabilities never trigger automatic launch; invalid declarations fail visibly. The download action opens the official Harness page.

The proxy authenticates through the desktop browser grant in memory. Healthy requests reuse the discovered target; a failed POST is never replayed. A target transport failure notifies the sidebar once, while local cancellation, page closure and disposal do not mark Desktop unavailable. Recovery keeps the existing iframe and its draft/session objects, shows a status banner and rediscovers the current Host. Automatic recovery only discovers: it must not undo an explicit Desktop exit or race the updater by launching the shell. Initial connection and explicit reconnect may request startup. The bounded recovery loop does not wait indefinitely; individual OS discovery and Host probes also have deadlines. DSH's own connection generation handling restores its streams and session baselines. Reachability does not prove completed session synchronization. Explicit reload, after preserving the draft, obtains the current desktop frontend and reinjects the private adapter.

EditorContext, ReferenceController, the loading animation and navigation remain local to the extension. DSH data writes occur through the Desktop Host's own interfaces. The desktop application and its installed files are not patched. Closing VS Code releases proxy sockets only.

The product source has four responsibility groups: `desktop/` owns discovery, process launch, authenticated forwarding and read-only update checks; `context/` owns editor snapshots; `references/` owns reference lifecycle; `sidebar/` owns presentation and the private DSH browser adapter. `extension.ts` wires their lifetimes and VS Code commands. Browser DOM assumptions stay in the adapter; update checks never access credentials, the proxy or session state.

`DesktopUpdates.check()` owns request coalescing, a six-hour success cache, installed-channel selection, semantic version comparison and cancellation. The extension presents notifications and remembers the last notified version. Windows file-version metadata identifies the installed application; `app-update.yml` selects the channel, with the upstream nightly default when no channel is supplied. Only fixed official feed URLs are requested. Failures reject rather than claiming the installation is current. Updating remains a user action through the official page.

The VSIX excludes runtime/ entirely. Legacy runtime source is isolated under `tests/fixtures/legacy-runtime/`, with preparation scripts retained for its historical tests. Packaging stages a fixed list of public assets before VSCE runs, so local runtime and editor caches are never traversed as candidates. Legacy Companion data is preserved without an automatic merge. Existing hosted workflows need an installed-desktop fixture before the next publication; this preview has local evidence only.

The coordinated Desktop source patch and its capability schema are described in [shared-session-solution.md](shared-session-solution.md). It is delivered as a separately built Desktop installer; Companion does not patch installed binaries or make stock 0.2.1-rc.2 attach to an independent Host.
