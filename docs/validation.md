# Validation: 0.3.2

## Startup I/O investigation (0.3.2)

Baseline is the installed 0.3.1 source commit 1b0fc84. A debug-only staged runtime reproduced 23,676ms to authenticated HTTP readiness in an empty home. Of that, core initialization took 21,890ms; migration was 8ms. Synchronous readFileSync observations totaled approximately 18.49s. CPU usage was 3.09s user plus 1.58s system; no external Undici request was observed. Asynchronous filesystem durations overlap synchronous blocking and must not be added to those wall times. This locates the large wait in startup file access, not historical migration; it does not prove whether the operating-system cache, scanning or another filesystem factor caused each cold read to stall.

Subsequent baseline measurements read roughly 2,741 distinct files through 4,300 synchronous reads. TypeBox accounted for 669 files, the largest leaf package. A freshly extracted VSIX at a normal-length test path started in 3,703/3,142ms after its separate extraction step. Core initialization was 2,656/2,630ms. A staged TypeBox bundle reduced its actual core-start reads to 15 files and core initialization to 2,349/2,375ms; total readiness was 2,868/2,885ms. These process starts did not flush the operating system's file cache, so they are not guarantees for a machine's first disk-cold opening.

A controlled slow-filesystem replay added waits before each first dependency-file read. It reduced total startup from 43,679ms to 33,509ms, about 23%, and delayed files from 2,728 to 2,071. This is an artificial stress comparison, not an actual 25-second cold-start benchmark; Windows wait granularity also makes each nominal 7ms delay longer in practice. A new deterministic regression first failed on 670 TypeBox file reads, then passed with 26 reads while importing all nine public entry points. It also checks export names/types/function names against the pristine 1.3.27 contract, compiled and interpreted validation, shared format registry and namespace identity.

The optimization runs at dependency preparation time with esbuild shared ESM chunks. Public paths and adjacent TypeScript declarations are retained; Node, DSH and provider versions are unchanged. No production global filesystem hook or persistent compile cache is introduced. Diagnosis also exposed a control-pipe EOF at old-owner exit; a deterministic real-pipe test reproduced it, and RuntimeClient now retries this handshake without launching a competing host or replaying chat traffic.

Final verification: typecheck, build/package and all 21 automated checks passed. Standards and Spec reviews reported no remaining actionable findings. Microsoft VS Code installed 0.3.2 successfully; its extension entry matched the build SHA-256 and its bundled TypeBox passed the nine-entry export/behavior contract with 26 file reads. A real VS Code Webview using that installed runtime and a fresh owned data home reached backend readiness in 3,118ms, showed the preview notice 705ms after frame bootstrap, dismissed it 296ms after clicking and verified the saved acknowledgement. This does not flush the OS file cache and does not establish a disk-cold upper bound. No paid model calls were made and the desktop application/data were not modified.

## Windows Webview confirmation regression (0.3.1)

VS Code supplies a lowercase drive prefix in extension URI paths. With that spelling, the DSH package router and Node could load separate instances of module-scoped boot state. The real Webview's preview acknowledgement returned HTTP 200 with business failure `settings/rejected`: `dsh: profile reload requires the root Include entry`. A direct shell launch using an uppercase drive prefix had hidden this failure in 0.3.0 acceptance.

RuntimeClient now resolves the runtime directory with the native filesystem realpath before choosing the Node executable, host entry, manifest and working directory. It preserves one module identity without patching upstream code, bypassing the notice, or editing desktop data. A new regression test first reproduced the failure and then passed, including persistence across runtime restart. The opt-in tests/native-welcome.cjs drives the actual notice button in a real VS Code Webview and checks both modal dismissal and saved Host settings. The fixed native run measured backend readiness at 2,841ms, notice visibility 703ms after frame bootstrap and dismissal 297ms after clicking.

Startup phase sampling with real source history measured approximately 1.29s for first migration and 2.71s for core boot. One earlier cold run took 25.05s before readiness; this was not stable across repeats, and its additional delay has not been attributed to a specific cause. In a five-run empty-home comparison, startup without Node compile cache was 2,515/2,487ms, versus 2,639ms for first cache use and 2,587/2,573ms with a populated cache. Compile caching was therefore not added. These local runs do not establish a worst-case startup limit or show that every slow opening has been eliminated.

## Independent runtime acceptance (0.3.0)

Validated on Windows x64 with VS Code 1.124.2. The packaged core is DSH 0.2.1-rc.2, WorkBuddy 0.6.10 at the recorded public commit, and Node 24.21.0. No paid model calls were made.

`npm run check`, build and all 18 automated checks passed. The cold-start check was then extended and rerun successfully to cover two independent homes coexisting with distinct PIDs/ports. Tests cover concurrent clients sharing one core, last-client shutdown, owner-pipe retention throughout saving, version handoff during the reconnection grace, rapid real startup failure followed by recovery, one-time read-only migration, skipped unfinished history, only referenced attachments, credential isolation, authenticated HTTP/SSE/WebSocket forwarding, no POST replay, context serialization and draft restoration.

A fresh real desktop-data snapshot imported 66 completed sessions, 68 log-generation files and two referenced attachments; one interrupted/pending session was skipped. All 7,476 inspected source files retained their SHA-256 hashes. Startup plus proxy/HTTP validation and the second source hash scan took 7,886ms. HTTP returned 200 and included the Companion adapter bootstrap. Earlier empty-home cold startup took about 6.4s. These are local measurements, not startup service guarantees.

The final VSIX was installed through the real Microsoft VS Code CLI. An isolated native VS Code run loaded that installed extension directory, version 0.3.0, started its bundled Node/core with a separate globalStorage home, and verified dynamic readiness. Native editor checks passed for multi-root binding, unsaved selection, latest buffer, focus retention, authorized file reads, open command and actual Webview transport. Final Webview load plus context/read/result roundtrip was 181ms. Installed host/import files matched the final build hashes. Existing user windows were not forcibly reloaded.

The real bundled DSH GUI was checked at 400px width through a simulated editor bridge. A local interceptor returned intentional HTTP 503 for the prompt, so no model received it. Exactly one request contained the selected snapshot and excluded the full buffer. The first sampled frame cleared the input after 24ms; the failed draft returned after 485ms. Reference serialization measured 0.9ms and local send feedback 1.1ms. The page had no horizontal overflow or extra reference buttons. Screenshot evidence is delivered separately.

These measurements distinguish local feedback from model/network latency. They do not establish end-to-end native prompt latency, large-file responsiveness, account login success or model first-token latency. WorkBuddy requires a fresh login. Tests verify independent homes can coexist, but the official desktop application's simultaneous window flow was not exercised in this round. Production code neither starts nor controls that desktop application. Arbitrary third-party desktop plugins and workspace pin/order/archive metadata are not migrated. Custom drag/drop remains deferred.

The previous 0.2.0 hidden desktop-launch implementation is superseded; its acceptance evidence remains in Git history. For 0.3.0, use docs/spec.md and ADR 0001 as the current contract.
